# The tree sorts by kind, then by area and topic

A spec file must be below one of these kind folders.

| Folder | Kind | Content |
| --- | --- | --- |
| `requirements/functional/` | `functional` | What the product must do. |
| `requirements/non-functional/` | `non-functional` | How well the product must do it: security, privacy, performance, usability, accessibility. |
| `protocols/` | `protocol` | The formats that the product exchanges: messages, payloads, files and exports. |
| `structures/` | `structure` | The structures of the product as UML diagrams in Mermaid. |
| `style/` | `style` | How code and tests must look. |
| `conventions/` | `convention` | How specs must look. |
| `workflow/` | `workflow` | How people and agents must work: changes, reviews, commits and pull requests. |
| `agents/` | `agent` | What only an agent must do or must not do. |
| `decisions/` | `decision` | One design decision with its alternatives (000042). |

A rule must go to the first kind of this list that applies to it:

1. It records why the product uses one solution and not a different one: `decision`.
2. It controls the behavior of the product: `functional` or `non-functional`.
3. It controls a format that the product exchanges: `protocol`.
4. It controls the structure of the code: `structure`.
5. It controls how code or tests look: `style`.
6. It controls how specs look: `convention`.
7. It controls how people and agents work: `workflow`.
8. It applies only to agents: `agent`.

Below the kind folder, the first folder is the area, for example `meetings/`. The folder below
it is the topic, for example `voting/`. The topic folder holds the rule files.

Reason: The kind tells the reader what type of rule to expect. The list gives one kind to
each rule, so that two agents put the same rule in the same folder. Area and topic put the rules of
one part of the product side by side.

Test: `specs check`.
