# The tree sorts by kind, then by area and topic

A spec file must be below one of these kind folders.

| Folder | Kind | Content |
| --- | --- | --- |
| `requirements/functional/` | `functional` | What the product must do. |
| `requirements/non-functional/` | `non-functional` | How well the product must do it: security, privacy, performance, usability, accessibility. |
| `protocols/` | `protocol` | The formats that the product exchanges: messages, payloads, files and exports. |
| `structures/` | `structure` | The structures of the product as UML diagrams in Mermaid. |
| `style/` | `style` | How code and tests must look. |
| `conventions/` | `convention` | How specs must look. |
| `workflow/` | `workflow` | How people and agents must work: changes, reviews, commits and pull requests. |
| `agents/` | `agent` | The rules that apply only to agents. |
| `decisions/` | `decision` | One design decision with its alternatives (spec 000042). |

Reason: The kind tells the reader what type of rule to expect.

Test: `spezi check`.
